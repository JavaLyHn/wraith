# 技术文档写作（Documentation Writing）

## 概述

好文档让代码可维护、团队可协作、用户可上手。

**核心原则：文档为读者写，不为作者写。读者需要什么就写什么，不多不少。**

## 文档类型与模板

### README.md

```markdown
# 项目名

一句话说明项目做什么、给谁用。

## 快速开始

  最少步骤跑起来（3 步以内）

## 功能特性

  核心能力列表（每条一句话）

## 安装

  前提条件 + 安装命令

## 使用

  最常见的 2-3 个用法示例（可运行的代码）

## 配置

  关键配置项表格（名称 / 默认值 / 说明）

## 开发

  本地开发环境搭建 + 测试命令

## 许可证
```

**原则：**
- 30 秒内让读者知道「这东西值不值得我花时间」
- 快速开始必须可直接执行，不能有隐含前提
- 示例代码必须能跑，不是伪代码

### API 文档

每个公开 API 需要：

```
方法签名 + 一句话说明

参数：
  - name (类型): 说明。必填/可选。默认值。约束。

返回：
  - 类型: 说明。

异常/错误：
  - 条件 → 抛什么异常/返回什么错误码

示例：
  一个最简可运行的调用示例

注意事项：
  边界行为、线程安全性、性能特征
```

### 架构文档

```markdown
# 系统架构

## 概览
  一段话 + 一张图说明整体结构

## 核心组件
  每个组件：职责、接口、依赖关系

## 数据流
  主要场景的数据如何流经系统

## 关键决策
  为什么选 A 不选 B（ADR 风格）

## 部署拓扑
  生产环境如何部署

## 约束与边界
  不做什么、已知限制
```

### 变更日志（CHANGELOG）

```markdown
## [版本号] - YYYY-MM-DD

### 新增
- 用户可感知的新功能

### 变更
- 行为变化（尤其是破坏性的）

### 修复
- 修了什么 bug

### 移除
- 移除了什么能力
```

## 写作原则

### 1. 倒金字塔：最重要的信息在最前

读者可能只看前三行。把「做什么」「怎么装」放最前，「为什么这么设计」放后面。

### 2. 示例 > 解释

```
❌ "该方法接收一个符合 RFC 5322 的邮箱字符串参数，
    经正则校验后返回布尔值。"

✅ isValidEmail("user@example.com")  // true
   isValidEmail("not-an-email")      // false
```

### 3. 具体 > 抽象

```
❌ "配置适当的环境变量"
✅ "设置 OPENAI_API_KEY=sk-xxx"
```

### 4. 保持同步

文档和代码不一致比没有文档更糟。
- 改了行为 → 同步文档
- 文档里的命令/示例 → 定期验证能跑
- CI 里加文档链接检查（检测死链）

### 5. 写给未来的自己

六个月后你不记得这段代码的上下文。此时文档值多少？

## 常见误区

| 误区 | 修正 |
|------|------|
| 注释重复代码 | 注释解释「为什么」而非「做什么」 |
| 文档过长无人读 | 分层：快速开始 → 详细指南 → 参考 |
| 只写怎么做 | 加上为什么这么做（决策背景） |
| 假设读者知道一切 | 列出前提、定义术语 |
| 文档写完不维护 | 每次改代码检查文档是否要跟 |

## 不要做的事

- ❌ 写了比代码还长的注释来解释一行代码做什么
- ❌ 在文档里放不能运行的示例代码
- ❌ 把实现细节写进面向用户的文档
- ❌ 用学术论文的语气写使用指南
- ❌ 维护多份重复的同一信息（单一来源原则）
