# 代码检索质量评测台

对一组**冻结的查询**跑真实检索，量 `R@k` / `MRR@10`，并能与上一次结果逐条对比出「好几条 / 差几条」。

存在的理由很直接：改检索（分块、打分、embedding 模型）**改完不知道是变好还是变坏**。没有这个台子，「优化了检索」这句话是不可证伪的。

## 用法

```bash
mvn package                                    # 需要 target/wraith-1.0-SNAPSHOT.jar
scripts/rag-eval/run-eval.sh --save-baseline   # 改动之前:存基线
# ... 改分块 / 改打分 / 换 embedding 模型 + 重建索引 ...
scripts/rag-eval/run-eval.sh --vs-baseline     # 改动之后:逐条对比
```

### 前提（缺一个就量不了，脚本会明确失败，不会静默给 0 分）

1. `target/wraith-1.0-SNAPSHOT.jar` 存在。
2. embedding 后端可用（走 `~/.wraith/config.json`；本机 ollama 或云端都行）。
3. **当前仓库已建过索引**，且索引的模型与当前配置一致。不一致时 `rag.search` 会抛维度错误，脚本直接失败 —— 那种情况下的分数没有意义，报出来比给个假分数好。

### 隔离（只读，但想完全不碰真实环境时）

`rag.search` 不写索引也不写 config。要彻底隔离：

```bash
WRAITH_EVAL_HOME=/tmp/eval-home    scripts/rag-eval/run-eval.sh   # 另一份 ~/.wraith(config + 索引)
WRAITH_EVAL_RAGDIR=/tmp/eval-rag   scripts/rag-eval/run-eval.sh   # 只换索引库,config 用真实的
```

## 它测的是真实实现，不是复刻

`eval.mjs` 走 app-server 的 `rag.search` RPC —— 也就是真实的 `CodeRetriever.hybridSearch` + 真实的 `RagQueryTokenizer`（jieba）+ 真实的打分。**刻意不做本地复刻。**

这条不是洁癖。2026-08-04 探索打分方案时用过一个 Python 复刻，它能逐位重现当前算法在几条抽查上的输出，但在完整的 24 条查询集上**与真实实现差了 2 条**：

| | R@10 | MRR@10 | 未命中 |
|---|---|---|---|
| 真实 Java | 58.3% | 0.2730 | 10/24 |
| Python 复刻 | 54.2% | 0.2693 | 11/24 |

差异出在「RPC 方法名怎么分发」（真实第 10 / 复刻未命中）与「桌宠 macOS 不激活」（真实第 10 / 复刻第 9）—— 大概率是并列分数的破平顺序（Java 的 `LinkedHashMap` 插入序 vs Python dict）。**复刻可以用来快速筛方案，但结论必须回到真实实现上复测。**

## 指标怎么读

三个指标只依赖一个数：**正确答案排在第几名**。

- **`R@k`**：正确答案进前 k 名的**题目占比**。严格说这里是命中率（hit rate）而不是召回率 —— 每条题只认一个目标。`R@3` 最有参考价值：`search_code` 默认返回 5 条，而模型基本只细看前几条。
- **`MRR@10`**：每条取 `1/名次`（第 10 名之外记 0），对全部题目求平均。**对头部极度敏感** —— 第 2 升第 1 贡献 +0.5，第 9 升第 8 只贡献 +0.014。这正好符合检索的价值分布，代价是「掉出前 10」会被重罚（直接归 0）。
- **好 / 差 计数**：`--vs-baseline` 给出。**样本小的时候它比百分比可靠** —— n=24 时一条题就是 4.2 个百分点。

## 查询集

`queryset.json`。每条：

```json
{ "q": "自然语言查询", "path": "正确答案的路径子串", "name": "可选:块名子串", "group": "分组标签" }
```

`path` 相对仓库根、大小写不敏感；`name` 为 `null` 时只看路径。

### 加题的规矩

- 加题只追加对象，**不要为了让某个方案变好而修改已有题目的 `path`/`name`**。
- 改题必须在**跑之前**改。看过结果再调题目就是拿题凑答案。
- 查询集的 md5 会打进结果文件与报告。跨查询集比总分没有意义，`--vs-baseline` 检测到 md5 变化会明确警告，那时只看逐条升降。

### 这套题的已知偏差（一起看，别只看分数）

1. **n=24，一条题 = 4.2 个百分点。** 百分比之间的小差别不要当真。
2. **出题人是 Claude，出题时它已在本仓库工作一整天** —— 措辞可能无意偏向它熟悉的文件。这是真实偏差，减轻它的唯一办法是仓库的人自己加题。**建议先加到 40+ 条再用它做参数选择**，否则在 24 条上挑冠军很难和过拟合区分。
3. 只在 wraith 这一个库、`bge-m3` 这一个模型上验过。别的库（尤其非中文、非 Java 为主）不保证同向。

## 已知的检索缺陷（这个台子量出来的）

截至 2026-08-04，基线 `R@1 16.7% / R@10 58.3% / MRR 0.2730`，未命中 10/24。已定位但**尚未修**的三处：

1. **超大方法不分块。** `CodeChunker.chunkJavaFile` 对方法没有大小上限，而 `EmbeddingClient` 的 `MAX_INPUT_CHARS=2000` 只截断**向量输入**、不截断存储。实测 `Main.startAppServer()` 是 80920 字符的一块，向量只覆盖 2.47% —— 里面全部 RPC 实现（`embeddingTest` 在第 48645 字符处）**从未进过任何向量**。这直接对应 A 组 6 条题基线 0/6 命中。
2. **关键词分会饱和到 1.05，超过语义满分 1.0。** `boostKeywordMatch` 的注释声明「最高 ~0.8，不会压过语义结果」，但漏算了双重命中 `+0.1` 与类型加分 `+0.15`。多个块同时撞顶后，组内顺序退化成插入序。
3. **`chunkLargeText` 的单行漏洞。** 判断只 flush 当前段，然后照样把超长行整个塞进新段 —— 一行几十 MB 的 minified js 就成了一个几十 MB 的块（实测某项目里有 38.91 MB 的单块），且其向量只由前 2000 字符算出，同时拖慢每一次全表检索。

模拟（Python 复刻，**未在真实实现上验证**）显示「分块修复 + 语义分保留幅度 / 关键词分只用名次倒数」这一组合可把 MRR 提到 0.48 量级，代价 1~2 条退化。落 Java 后必须用本台子 `--vs-baseline` 复测，别信模拟数。

## 输出

- `target/rag-eval/baseline.json` / `latest.json`：含 `querysetMd5`、`metrics`、逐条 `rows`。
- 终端打印逐条名次 + 汇总 + （对比模式下）逐条升降。
