# 逻辑原型

微型交互式终端应用，让用户手动驱动一个状态模型。问题关于**业务逻辑、状态转换或数据形态**——纸上看着合理、推过真实 case 才觉得不对的那种。

## 何时这是对的形态

- 「我不确定这个状态机处理 X 然后 Y 的边界 case。」
- 「这个数据模型真能表示……的情况吗」
- 「写之前我想摸出 API 该长什么样。」
- 任何用户想**按键看状态变**的场景。

问题是「这该长什么样」——错分支。用 `ui.md`。

## 流程

### 1. 陈述问题

写代码前，写下要原型化的状态模型和要回答的问题。一段话，放原型 README 或文件顶部注释。回答错问题的逻辑原型是纯浪费——把问题写明，便于之后核对，无论用户现在在看还是 AFK 回来。

### 2. 选语言

用宿主项目用的语言。项目没有明显运行时（如纯文档仓），就问。

匹配项目既有工具约定——别为原型引入新包管理器或运行时。

### 3. 把逻辑隔离进可移植模块

把真正回答问题的逻辑——那一块——放在一个小而纯的接口背后，日后可整体拎出塞进真实代码库。围绕它的 TUI 是一次性的，逻辑模块不该是。

形态取决于问题：

- **纯 reducer**——`(state, action) => state`。动作是离散事件、状态是单值时好用。
- **状态机**——显式状态与转换。「现在哪些动作合法」是问题的一部分时好用。
- **一组纯函数**作用于一个纯数据类型。没有隐式当前状态——只是变换时好用。
- **一个类或模块**带清晰方法表面，当逻辑真地拥有持续内部状态时。

选最贴合*要回答的问题*的形态，不是最好接到 TUI 的那个。保持纯：无 I/O、无终端代码、无用于控制流的 `console.log`。TUI import 它并调用；不该有反向流。

这让原型在自身寿命之外有用：问题答完后，验证过的 reducer / 机器 / 函数集可以单独拎进真实模块。

### 4. 建暴露状态的最小 TUI

建成**轻量 TUI**——每 tick 清屏（`console.clear()` / `print("\033[2J\033[H")` / 等价）并重渲整帧。用户永远看到稳定的一帧，不是不断增长的回滚。

每帧两部分，按序：

1. **当前状态**，pretty-print 且 diff 友好（一行一字段，或格式化 JSON）。字段名/小节标题用**粗体**，次要上下文（时间戳、ID、派生值）用**暗色**。原生 ANSI 转义码即可——`\x1b[1m` 粗体、`\x1b[2m` 暗、`\x1b[0m` 重置。除非项目已有样式库，否则不用引。
2. **键盘快捷键**，列在底部：`[a] 加用户  [d] 删用户  [t] 推进时钟  [q] 退出`。键加粗、描述暗，或反过来——怎么清楚怎么来。

行为：

1. **初始化状态**——单个内存对象/结构体。启动时渲第一帧。
2. **一次读一个键（或一行）**，派发给一个 mutate 状态的 handler。
3. **每次动作后重渲整帧**——不追加，替换。
4. **循环到退出。**

整帧应能一屏放下。

### 5. 一条命令跑通

给项目现成 task runner 加脚本（`package.json` scripts、`Makefile`、`justfile`、`pyproject.toml`）。用户跑 `pnpm run <prototype-name>` 或等价——永远不用记路径。

宿主项目没 task runner，就把命令放原型 README 顶部。

### 6. 交付

给用户运行命令。他们自己开；有意思的时刻是他们说「等等，这不该可能」或「嗯，我以为 X 会不一样」——那是*想法*里的 bug，正是全部意义。他们要加新动作就加。原型会演化。

### 7. 捕获答案与原型

原型答完问题，捕获答案，再按 SKILL.md 描述捕获原型。逻辑特定的映射：验证过的 reducer / 机器 / 函数集拎进真实模块（决策，吸收）；TUI 壳随到保留原型为一手来源的一次性分支。

## 反模式

- **别加测试。**原型是一次性的。
- **别抽象。**纯函数集或 reducer 就够。
- **别用真实 DB / 网络。**状态在内存。
- **别让 TUI 逻辑泄漏进逻辑模块。**逻辑模块保持纯、可移植。
- **别把原型直接提为生产。**重写一遍再折进去。
