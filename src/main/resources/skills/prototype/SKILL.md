# 原型（Prototype）

一次性代码，用来回答一个问题。问题决定形态。

## 选分支

从用户 prompt、周围代码、或（用户在的话）直接问，识别回答的是哪个问题：

- **「这个逻辑/状态模型对不对？」**→ `references/logic.md`。建一个微型交互式终端应用，把状态机推过纸上难推理的 case。
- **「这该长什么样？」**→ `references/ui.md`。在单一路由上生成几个截然不同的 UI 变体，用 URL search param + 浮动底栏切换。

两个分支产物差异很大——选错浪费整个原型。若问题真模糊且用户联系不上，默认选更贴合周围代码的那个分支（后端模块→逻辑；页面/组件→UI），并在原型顶部声明这个假设。

## 对两者都适用的规则

1. **从第一天起就是一次性的，并标清楚。**把原型代码放在它真正会被用到的地方旁边（它为之原型化的模块或页面旁），让上下文一目了然——但起名要让读者一眼看出是原型，不是生产代码。一次性 UI 路由要遵守项目既有路由约定；别发明新的顶层结构。
2. **一条命令跑。**用项目现成 task runner 支持的——`pnpm <name>`、`python <path>`、`bun <path>` 等。用户必须能不假思索启动。
3. **默认不持久化。**状态在内存。持久化是原型在*检验*的东西，不是它该依赖的东西。若问题明确涉及数据库，打一个 scratch DB 或本地文件，起个清楚的「PROTOTYPE — wipe me」名。
4. **跳过打磨。**不写测试、不写让原型跑起来之外的错误处理、不抽象。重点是快点学到东西。
5. **暴露状态。**每次动作后（逻辑）或每次切变体（UI），打印或渲染完整相关状态，让用户看到变了什么。
6. **完成后捕获。**把已验证的决策折进真实代码，再把原型本身作为**一手来源**捕获：提交到一次性分支（不在 main），在实现 issue 上留指向该分支的指针。也捕获答案——结论和它解决的问题——记到 issue 或 commit。main 分支只留已验证的决策。

## wraith 说明

- 原型代码仍受 PathGuard 约束（限定项目根内）；`create_project` 工具可起脚手架。
- 一次性分支可用 `revert_turn` 或 Side-Git 快照（`/snapshot`）隔离，避免污染主工作区。
- TUI 原型若需 ANSI 控制台转义，注意 Wraith inline renderer 会消费 stdout——原型建议放独立文件，由用户直接 `execute_command` 跑，而不是经 Agent 输出流。
