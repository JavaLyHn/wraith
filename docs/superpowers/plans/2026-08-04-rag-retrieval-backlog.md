**日期:** 2026-08-04 **状态:** 待办（范围开关已实现并合入，其余未动）
**闸门:** 每一项落地前后都必须跑 `scripts/rag-eval/run-eval.sh --vs-baseline`

> **这份清单的每一条都带实测数字**，因为这一轮的经验是：**凭直觉改检索会变差**。
> 我先后提了四版「改进」，其中三版在真实语料上实测是**变差的**：
>
> | 我提的方案 | 实测结果 |
> |---|---|
> | 语义/关键词归一化后加权 | MRR 0.2693 → 更差（丢掉了承重的关键词信号） |
> | + IDF + 类型加分降级为 tie-break | 好 6 差 5，R@1 反降 |
> | 排除 `file` 类型块 | **最差**（文档块正是「为什么这么设计」的答案） |
> | 硬夹关键词分 < 1.0 | **排序一个字没变**（并列项等量被夹，仍并列） |
>
> 所以：**没有评测台数据支持的检索改动，不要做。**

## P1 —— 有数据支持、方向明确

### T1. 分块修复：超大方法切段 + 超长单行硬切

**缺陷（已量化定位）**：

- `CodeChunker.chunkJavaFile` 对方法**没有大小检查**；而 `EmbeddingClient.MAX_INPUT_CHARS = 2000`
  只截断**向量输入**、不截断存储。
- 实测 `Main.startAppServer()` 是 **80920 字符**的一块，**向量只覆盖 2.47%** ——
  里面全部 RPC 实现（`embeddingTest` 位于第 48645 字符）**从未进入任何向量**。
- 全库 141 个方法块超限，**4.8%（43 万字符）从未被向量化**。
- `chunkLargeText` 的单行漏洞：判断只 flush 当前段，然后照样把超长行整个塞进新段 ——
  一行 38.91 MB 的 minified js 就成了一个 38.91 MB 的块（某项目实测）。

**离线模拟结果**：单独做这一条 = **好 2 差 0**，MRR 0.2693 → 0.2960（+10%）。
**安全但收益小** —— 因为切出来的段虽然进了向量空间（`Main.startAppServer()#25` 从「不存在」
变成纯语义第 13），却被当前打分压到第 58（前 10 名整片撞在关键词饱和分 1.0500）。
**所以它的价值是「T2 的前提」而不是独立收益。**

**必须做对的细节**：切段的 `name` 要**带上完整方法签名**，只在后面追加段号。关键词检索是
`name LIKE`，签名是这套检索唯一能用的强信号 —— 一切段就把 `formatFetchResult` 那类查询打坏。

**代价**：块数 9718 → 10029（+3.2%），需要重建索引。

### T2. 打分改造：语义保留幅度 + 关键词只用名次

**缺陷（已量化定位）**：语义分是连续量 `[0,1]`，关键词分是存在性标记（几档离散值），
两者**直接相加**。结果是关键词分能饱和到 **1.05 > 语义满分 1.0**：
`0.3` 底分 + `0.3` name + `0.1` file + `0.1` content + `0.1` 双重命中 + `0.15` method。
`boostKeywordMatch` 的注释声明「最高 ~0.8，不会压过语义结果」——**那个不变量已经破了**。

**离线模拟的最优形态**：

```
score = 余弦相似度 + 1.0 / (10 + 关键词名次) + 0.75 × 类型加分
        └─保留幅度─┘  └─只用名次,天然封顶 0.0909─┘  └─七五折─┘
```

模拟：MRR `0.2730 → 0.4876`（**+81%**），R@10 `58.3% → 75.0%`，**13 好 1 差**。

**三条都是被数据逼出来的**：
1. 语义侧**保留余弦**——纯 RRF（两侧都用名次）会让「余弦只差 0.0424、名次差 8 位」的正确答案被罚 42% 而掉出前 10（沙箱那条实测）。
2. 关键词侧**只用名次**——那一侧的分数本来就不可比，而 `1/(10+rank)` 最大 0.0909，天然封顶。
3. 类型加分**打七五折保留**，不是删掉。删过两次，两次都变差 —— 它在补偿 `file` 块（2000 字符的大语义单元离所有查询都不远）。扫出 `tb=0.25/0.5/0.75/1.0` → `12好2差 / 13好2差 / **13好1差** / 12好1差`。

**风险（必须承认）**：这三个参数是在 24 条上扫出来的，**过拟合风险最集中**。而且模拟用的是
Python 复刻，它与真实 Java 已经证明**差了 2 条题**。**所以 T0 是它的前提。**

### T3. IDF 加权（并入 T2 一起评）

`不要` 命中 151 块、`用户` 918 块、`桌面` 549 块，而 `抢走` 只有 3 块 —— **信息量差两个数量级，
底分却一样**。停用词表只有 11 个词，靠扩表治不了（数据自己知道哪些词没信息量）。

单独试过「整体乘 IDF」= 变差（把承重的信号压死了）。要做就得只压「超出底分的那部分」，
并且**和 T2 一起评**，不单独上。

## P2 —— 已定位，收益未量化

### T4. 单块内容上限

某项目索引里 5 个压缩 `.js` 占 **87 MB / 97 MB**，其中一个 38.91 MB 的块**向量只由前 2000 字符算出**
（语义上毫无意义），而 `VectorStore.search` **每次检索都 `SELECT ... content ...` 扫全表** ——
每查一次要把这 87 MB 过一遍 JDBC，只为了拿旁边那列向量。

**要定的决策**：超过多大的文件不索引 / 内容存多少（存全文是为了给模型看代码片段，
但 `rag.search` 回包本来就截到 500 字符）。这是个**取舍决定，不是纯 bug**，所以要人拍板。

### T5. 分块重叠（10~15%）

现在按行硬切、**零重叠**，切点落在语义中间时两边都表达不好。收益未量化。

### T5b. 给 `rag.index.progress` 事件加结构化字段

事件现在只带一个 `message` 字符串（`CodeIndex.ProgressListener` 的签名就是 `String`），
所以桌面的进度条是**解析显示串**取出 `done/total/percent/file` 的。

这个耦合是有意识的（改 `ProgressListener` 签名会波及 CLI 与一批调用点），并且对冲了：
`IndexProgressDetailTest#progressLineShapeIsParsedByDesktop` 钉住那一行的形状，
改文案会让它变红并在失败信息里指出要同步改 `indexProgressView.ts`。
**但守门人只是让它不会静默坏掉，不等于不该修。** 正解是事件里直接带
`{phase, done, total, percent, file}`，桌面不再认文案。

### T6. `file` 段的语义标签

现在 `file` 段的 `name` 是 `路径#3` —— 关键词检索对它们等于失效（name 里只有路径），
模型在结果里看到的也只是 `路径#3`。可以补「文件名 + 段内首个标题/首行」。

### T7. 给关系图谱加 agent 工具

`code_relations` 有 55091 条边（`calls` 46630 / `contains` 5613 / `imports` 2687 /
`implements` 99 / `extends` 62），但**只有 REPL 与面板两个入口，没有对应的 agent 工具** ——
模型永远用不到。另外 `VectorStore.getOutgoingRelations` 是**死代码**，没有任何调用点。

注意它**不是真图**：查询是 `WHERE from_name = ? OR to_name = ?`，一跳到底、没有递归、
没有节点表，「节点」就是裸名字字符串。要做 agent 工具就得先决定是否支持多跳。

## P3 —— 知道该做但不在本项目范围

### T8. Reranker / Cross-encoder

两阶段检索的标准做法，而它**恰好能治 T2 的根因**：交叉编码器直接输出统一尺度的相关度，
**不需要拍权重**。没做的原因是额外一次模型调用（本机 ollama 上是实打实的延迟）。

### T9. ANN 索引（HNSW / IVF-PQ）

现在是暴力全表扫。9718 块这个量级是合理取舍（省掉一个索引组件及其一致性维护），
**十万级以上就该换**。

### T10. 语义去重（MMR）

现在是穷人版 `limitPerFile(结果, topK, 2)` —— 同一文件最多 2 条，**没有语义去重**，
所以同一文件的两个雷同段落仍会双双占位。
