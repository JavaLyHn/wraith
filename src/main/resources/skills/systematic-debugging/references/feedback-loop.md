# 反馈循环调试法（Feedback Loop）

补强 `systematic-debugging` 的根因调查阶段：对**难 bug 和性能回归**，把「建一条紧的 pass/fail 反馈循环」当作第一性技能。这是整个调试的核心；其余都是机械操作。

> 来源：Matt Pocock 的 `diagnosing-bugs` 技能，经 Wraith 改写整合进 systematic-debugging 的阶段一。

## 为什么先建循环

如果你有一条**紧的** pass/fail 信号——一条能在这个 bug 上变红的信号——你就能找到根因：二分、假设检验、埋点都只是消费它。没有的话，盯着代码看到天亮也救不了。

在这个阶段花不成比例的精力。**激进、有创意、不放弃。**

## 构建方式（大致按此序试）

1. **失败测试**——在能触及 bug 的任一接缝：单元、集成、e2e。
2. **curl / HTTP 脚本**——对跑着的 dev server。
3. **CLI 调用**——带 fixture 输入，stdout 对已知快照 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，断言 DOM/console/network。
5. **回放捕获的 trace。**——存一条真实网络请求/载荷/事件日志到盘，隔离地回放过代码路径。
6. **一次性 harness。**——起系统最小子集（一个服务、mock 掉依赖），一次函数调用走 bug 代码路径。
7. **性质/模糊循环。**——若 bug 是「有时输出错」，跑 1000 个随机输入找失败模式。
8. **二分 harness。**——bug 出现在两个已知状态间（commit、数据集、版本），自动化「起在状态 X、检查、重复」让 `git bisect run` 能跑。
9. **差分循环。**——同一输入过旧版 vs 新版（或两配置），diff 输出。
10. **HITL bash 脚本。**——最后手段。若必须有人点，用 `scripts/hitl-loop.template.sh` 驱动他们，让循环仍结构化。捕获的输出回流给你。

建对循环，bug 90% 修好了。

## 收紧循环

把循环当产品。有了*一条*循环后**收紧**它：

- 能更快吗？（缓存 setup、跳无关 init、缩窄测试范围。）
- 信号能更锐吗？（断言具体症状，不是「没崩」。）
- 能更确定吗？（钉时间、seed RNG、隔离文件系统、冻结网络。）

30 秒的 flaky 循环勉强比没循环好；2 秒的确定性循环是紧的——调试超能力。

## 非确定性 bug

目标不是干净复现而是**更高复现率**。把触发跑 100×、并行、加压、缩时间窗、注入 sleep。50% 的 flake bug 可调试；1% 不行——持续提率直到可调试。

## 真的建不了循环时

明确停下说清楚。列出试过什么。向用户要：(a) 能复现的环境访问，(b) 捕获的工件（HAR、日志 dump、core dump、带时间戳的录屏），或 (c) 加临时生产埋点的许可。**不要**在没循环的情况下进假设阶段。

## 完成判据——一条能变红的紧循环

阶段一（根因调查）这一部分做完了，当循环**紧**且**能变红**：你能点名**一条命令**——一个脚本路径、一次测试调用、一个 curl——你已经**至少跑过一次**（贴出调用和输出），且它：

- [ ] **能变红**——走真实 bug 代码路径并断言**用户的精确症状**，所以它能在本 bug 上变红、修好变绿。不是「跑了不报错」——它必须能*抓到这个具体 bug*。
- [ ] **确定**——每次同一结论（flaky bug：钉住的高复现率，见上）。
- [ ] **快**——秒级，不是分钟级。
- [ ] **agent 可跑**——你能无人值守跑它；人在环里只经 `scripts/hitl-loop.template.sh`。

如果你发现自己在这条命令存在前就先读代码建理论，**停——直接跳到假设正是这个技能要防的失败。**没有能变红的命令，不进阶段二。
