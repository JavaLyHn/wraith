# UI 原型

在单一路由上生成几个截然不同的 UI 变体，用 URL search param + 浮动底栏切换。问题关于「这该长什么样」。

## 何时这是对的形态

- 「设置页该长什么样？」
- 「这几个布局哪个对？」
- 任何用户想**翻着看**的场景。

问题是「这逻辑/状态模型对不对」——错分支。用 `logic.md`。

## 选子形态

### 子形态 A：既有页面

最常见。已有页面要重新设计。在**现有路由**上挂变体切换器，用 `?variant=` 在原地表切换。数据获取留在切换器上方，只渲染子树随变体变。

### 子形态 B：新页面/路由

还没有页面，从零探索。在一个明确标记为一次性的路由上挂同样的切换器。用项目既有路由约定（如在路径里含 `prototype`）。同样的 `?variant=` 模式。

提交子形态 B 前自检：真没有既有页面能嵌进去吗？空路由会藏住有内容时会暴露的设计问题。

两种子形态的浮动底栏相同。

## 流程

### 1. 陈述问题并选 N

默认 **3 个变体**。超过 5 个就从截然不同退化成噪音——封顶。

一行写下计划，放原型位置或文件顶部注释：

> 「设置页三个变体，用 `?variant=` 切换，挂在现有 `/settings` 路由。」

无论用户在不在都能用。

### 2. 生成截然不同的变体

起草每个变体。每个要满足：

- 页面目的和它能拿到的数据。
- 项目的组件库 / 样式系统（TailwindCSS、shadcn、MUI、纯 CSS，什么都行）。
- 清晰的导出组件名，如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构上不同**——不同布局、不同信息层级、不同主交互，不是只换颜色。三个微调的卡片网格不是 UI 原型，是壁纸。两个草稿太像，就重做一个并明确「不准用卡片网格」。

### 3. 接到一起

在路由上建一个切换器组件：

```tsx
// 伪代码——适配项目框架
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形态 A（既有页）：所有现有数据获取留在切换器上方；只有渲染子树随变体变。

子形态 B（新页）：`/prototype/<name>` 下的一次性路由挂同一个切换器。

### 4. 建浮动切换器

屏幕底中一个小型固定位置条，三块：

- **左箭头**——切上一个变体（循环）。
- **变体标签**——显示当前变体 key，若变体导出名也显示。如 `B — 侧栏布局`。
- **右箭头**——切下一个（循环）。

行为：

- 点箭头更新 URL search param（用框架路由——Next 的 `router.replace`、React Router 的 `navigate` 等），让变体可分享、reload 稳定。
- 键盘：`←` `→` 也切换。`<input>`、`<textarea>`、`[contenteditable]` 聚焦时不拦截方向键。
- 视觉上与页面区分（如高对比药丸、轻微阴影），让人一眼看出不属于被评估的设计。
- 生产构建里隐藏——gate on `process.env.NODE_ENV !== 'production'` 或等价检查，免得误并的切器上线。

把切换器放一个共享组件里，两种子形态都能复用。放项目里共享 UI 所在处。

### 5. 交付

给出 URL（和 `?variant=` key）。用户有空就翻。有意思的反馈常是**「我想要 B 的头部配 C 的侧栏」**——那才是他们真要的设计。

### 6. 捕获答案并清理

变体胜出后，捕获答案——哪个变体、为什么——再按 SKILL.md 描述捕获原型。把赢家折进真实代码，其余移到一次性分支，不进 main：

- **子形态 A**——把赢家折进既有页；从 main 丢掉输的变体和切换器。
- **子形态 B**——把赢家提升为真实路由；从 main 丢掉一次性路由和切换器。

完整变体集是一手来源，所以进一次性分支，不进回收站——留在 main 的变体组件和切换器很快腐烂、困惑下一个读者。

## 反模式

- **变体只在颜色或文案上不同。**那是微调，不是原型。真变体在结构上不同意。
- **变体间共享太多代码。**共享 `<Header>` 行；共享 `<Layout>` 就毁掉意义。每个变体应能丢掉布局。
- **把变体接到真实 mutation。**只读原型行。变体要 mutate，指向 stub——问题是「这该长什么样」，不是「后端能不能用」。
- **把原型直接提为生产。**变体代码是在原型约束下写的（没测试、错误处理最小）。折进去时正经重写。
