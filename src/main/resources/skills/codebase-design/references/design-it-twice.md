# 两次设计（Design It Twice）

当用户要为选定的加深候选探索替代接口时，用这个并行子代理模式。基于「Design It Twice」(Ousterhout)——你的第一个想法不太可能是最好的。

使用 SKILL.md 的词汇——**模块**、**接口**、**接缝**、**适配器**、**杠杆**。

## 流程

### 1. 框定问题空间

派生子代理前，为选定候选写一段面向用户的问题空间说明：

- 任何新接口都得满足的约束
- 它要依赖什么、依赖落在哪一类（见 `deepening.md`）
- 一段粗略示意代码把约束落具体——不是提案，只是让约束可触

先给用户看，然后立刻进第 2 步。用户边读边想，子代理并行干活。

### 2. 派生子代理

用 Multi-Agent（`/team`）并行派生 3+ 个子代理。每个必须为加深模块产出**截然不同**的接口。

每个子代理一份独立技术简报（文件路径、耦合细节、`deepening.md` 里的依赖类别、接缝背后是什么）。简报独立于第 1 步的用户向问题空间说明。给每个代理不同的设计约束：

- 代理 1：「最小化接口——目标 1–3 个入口点。最大化每入口点的杠杆。」
- 代理 2：「最大化灵活性——支持多用例与扩展。」
- 代理 3：「为最常见的调用方优化——让默认情形平凡。」
- 代理 4（若适用）：「围绕端口与适配器设计跨接缝依赖。」

简报里同时带上 SKILL.md 词汇与项目领域语言，让各代理命名与架构语言、项目领域语言一致。

每个子代理输出：

1. 接口（类型、方法、参数——加不变量、顺序、错误模式）
2. 使用示例，展示调用方怎么用
3. 接缝背后藏了什么实现
4. 依赖策略与适配器（见 `deepening.md`）
5. 权衡——哪里杠杆高、哪里薄

### 3. 呈现与比较

顺序呈现各设计，让用户逐个吸收，再用散文比较。按**深度**（接口处杠杆）、**局部性**（改动集中在哪）、**接缝放置**对比。

比较后给出自己的推荐：你认为哪个最强、为什么。若不同设计的元素能合并，提出混合方案。要有主见——用户要的是一个强判断，不是一份菜单。
