# ADR 格式

ADR 放在 `docs/adr/`，顺序编号：`0001-slug.md`、`0002-slug.md` 等。

`docs/adr/` 目录懒创建——只在第一个 ADR 需要时建。

## 模板

```md
# {决策短标题}

{1–3 句：什么上下文、决定了什么、为什么。}
```

就这样。一个 ADR 可以只有一段。价值在于记下*做了*什么决定和*为什么*——不在于填满各小节。

## 可选小节

只在真有附加价值时加。大多数 ADR 不需要。

- **Status** 前言（`proposed | accepted | deprecated | superseded by ADR-NNNN`）——决策被重访时有用
- **Considered Options**——只在被否的替代值得记住时
- **Consequences**——只在非显然的下游效应需要点出时

## 编号

扫 `docs/adr/` 取最高现存编号，加一。

## 何时提议 ADR

三者全中：

1. **难逆转**——改主意的代价实质
2. **没有上下文会令人困惑**——未来读者看代码会想「他们为什么这么做」
3. **真正权衡的结果**——有过真实替代方案，你因特定理由选了这个

易逆转就跳过——你反手就改了。不令人困惑也没人会问为什么。没有真实替代就除了「我们做了显然的事」没别的可记。

### 什么算数

- **架构形态。**「用 monorepo。」「写模型 event-sourced，读模型投影到 Postgres。」
- **上下文间集成模式。**「Ordering 与 Billing 走领域事件，不是同步 HTTP。」
- **带锁定的技术选型。**数据库、消息总线、认证 provider、部署目标。不是每个库——只是那些换掉要一个季度的。
- **边界与范围决策。**「Customer 数据归 Customer 上下文拥有；其它上下文只按 ID 引用。」显式的 no 和 yes 一样值钱。
- **对显然路径的刻意偏离。**「我们手写 SQL 不用 ORM，因为 X。」任何合理读者会假设反面的。这些阻止下一个工程师去「修」一个刻意的东西。
- **代码里看不见的约束。**「因为合规我们不能用 AWS。」「响应必须 200ms 内，因为合作方 API 合约。」
- **非显然的否决。**考虑过 GraphQL 选了 REST 因微妙理由，记下来——否则六个月后又有人提 GraphQL。
